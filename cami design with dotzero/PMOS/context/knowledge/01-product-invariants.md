# Product Invariants
**Last updated:** 2026-08-03 **What this is:** Rules that must always hold true across every Cami flow. If a spec, design, or line of code violates one of these, the spec is wrong, not the invariant. Two types: 🔒 permanent principles (change only via a [Decision Record](04-decision-records.md "04-decision-records.md")) and 🕒 current constraints (true today, will lift as the product matures).

> **Two clarifications from the CamiPay design docs (2026-08-03), flagged not silently rewritten:**
> - **INV-P1 scope.** "Every in-platform appointment checkout goes through CamiPay" means Cami owns the commercial record (INV-P2), not that every tender is a gateway capture. Cash and off-rail card are recorded straight to the sale ledger (no gateway); only the payment link and terminal are CamiPay rails. Gift card is a stored-value tender. The signal to watch stays captured-vs-booked volume (EC-19).
> - **INV-P3 exception (terminal Phase 1).** The provider-abstraction invariant is temporarily bypassed by terminal Phase 1, which trusts a device report and does not call NeoPay/MPGS. Phase 2 restores gateway confirm. Treat Phase 1 as a known, time-boxed exception, not a repeal.

## Sales and ledger invariants (INV-01 to INV-11)

> Incorporated from Michelle's sales-domain invariant set (Slite draft, 2026-07-31). These are cross-cutting financial/ledger correctness rules and keep their original bare-number IDs (cited in Linear tickets and rule tables). They complement the payment/booking invariants above; the payments-specific INV-P10 (deposit = liability) is a consequence of INV-01 (append-only), and INV-04 here is the canonical void/refund definition behind the checkout state machine.

| ID | Invariant | Detail |
|----|-----------|--------|
| INV-01 | Catalogue objects are mutable; financial records are append-only. | A merchant may rename, reprice, or retire a service, product, gift card, or package anytime. None of those edits reach an already-created transaction. Invoices, payments, refunds, and ledger entries are never edited in place. Every reversal writes a new record. |
| INV-02 | Archive, never delete. | Removing an item from Settings means archive: stops new sales, does not void pending transactions, revoke issued entitlements, or remove history. Hard delete only for objects never transacted against. |
| INV-03 | Balances are derived, not stored. | Gift card balance, package sessions remaining, loyalty points are computed from an append-only event ledger, never a mutable integer. Ledger events: issue, hold, release, redeem, refund, void, adjust, expire, transfer. Any balance is reconstructable at any time; concurrent access cannot double-spend. |
| INV-04 | Void and refund are different operations. | Void = the transaction never happened (full, automatic, no user choice, no credit note). Refund = it happened and is being reversed (original record preserved, credit note issued, side effects reverse conditionally). Never one control with a toggle. |
| INV-05 | Money returns to the tender it came from. | Refunds go back to the original method; gift-card payments return to the gift-card balance; split tenders refund proportionally. Deviating needs an explicit permission gate and a stored reason. Refunding a non-cash tender as cash is a standard fraud vector. |
| INV-06 | A single reversal never gives back twice. | If cash is returned, entitlement is not restored, and vice versa. Exactly one path per reversal. The most likely correctness bug in sales; assert it in tests (see EC REV-E5). |
| INV-07 | Entitlement is held at intent, committed at capture. | Booking or add-to-cart places a hold; payment capture or invoice completion commits; abandonment releases. Applies to gift-card balance, package sessions, product stock. Without a hold, concurrent redemption double-spends. |
| INV-08 | Every state change is attributable. | Actor, timestamp, and where applicable a reason string. Overrides always require a reason. No silent mutations, no untraceable system-actor changes. |
| INV-09 | A zero-amount invoice is a valid invoice. | When a package or promotion covers the full amount, the invoice still exists, lists line items at full retail, shows AED 0.00 with the covering tender named. The invoice is the revenue, commission, tax, and proof-of-service event; suppressing it breaks all four. |
| INV-10 | A default beats a setting. | Configuration is added only where merchants genuinely differ in a way that changes their outcome. Preference, uncertainty, and internal disagreement are not reasons to make something configurable. Every setting declares its Business/Location inheritance level before shipping. |
| INV-11 | Every rule has an ID and every ticket cites one. | Business rules carry stable IDs; Linear issues and test cases reference the rule they implement/verify. A bug is traceable to an intent, or the intent was never written down. |
| INV-12 | Config changes apply forward-only. | Payment policy, gift-card presets/expiry, and promotions apply to new records only; existing bookings, sold cards, and discounted sales keep the terms they were created under. Source: business-rules-v2 payment-policy r9, gift-cards r21, promotions r11. |
| INV-13 | Precedence is fixed and nearest-wins. | Payment policy resolves booking override → service override → business default. Discounts resolve at most one promotion per line → then the ad-hoc cart discount → then tax. Totals resolve line prices → cart discount → tax (prices tax-inclusive, tax back-calculated). The reschedule window is clamped to the refundable window. **The totals clause is the coarse form of the Composition Order**, see [06 Money Composition Contract](06-money-composition-contract.md) §2 for the full sequence. Source: business-rules-v2 payment-policy, promotions r10, checkout r12. |

## Money composition invariants (INV-M1 to INV-M8)

> Registered here, **defined in** [06 Money Composition Contract](06-money-composition-contract.md) §5. These are the machine-checkable assertions on how money objects compose onto one invoice. They are automated tests; a failing INV-M is a release blocker. Do not restate them elsewhere, cite the ID.

| ID | Invariant | Type | Rationale |
|----|-----------|------|-----------|
| INV-M1 | `taxable_gross = Σ line_gross_final` | 🔒 | Taxable gross is derived from lines, never entered or stored independently. |
| INV-M2 | `vat_total = Σ round(line_gross_final × 5 / 105)` | 🔒 | VAT is derived per line from tax-inclusive gross, rounded once. Never appended, never rounded twice (06 §7). |
| INV-M3 | `amount_due = taxable_gross + tip` | 🔒 | **Currently violated by `/payments`**, which reads a balance computed without the tip. Root cause is a Scope Rule violation: the tip was treated as payment-scoped when it is invoice-scoped (06 §3). |
| INV-M4 | `Σ tender = amount_due` at settled state | 🔒 | A sale cannot settle over- or under-tendered. Change due is not a payment line (glossary). |
| INV-M5 | `tip ∉ tax_base` | 🕒 | True for a voluntary tip. Lifts or splits if a mandatory service charge object ships (06 §9.1, taxable consideration). |
| INV-M6 | `line_gross_final ≥ 0` for every line | 🔒 | No negative line on a sale. Reversals are separate negatively-signed documents (INV-01, INV-04). |
| INV-M7 | `Σ discounts ≤ Σ eligible_line_gross_pre_discount` | 🔒 | Discount can zero a line, never invert it. Package-redeemed lines are not discount-eligible (06 §2 step 4). |
| INV-M8 | `gift_card_redeemed ≤ gift_card_balance_at_time_of_capture` | 🔒 | Balance is derived, not stored (INV-03); the hold at intent prevents concurrent double-spend (INV-07, EC GC-E2). |

**Scope Rule (06 §3) is load-bearing and not restated here.** An invoice-scoped object (line price, line/cart discount, package redemption, **tip**) must be persisted to the invoice before any payment request. A payment request may not introduce an invoice-scoped object as request-only data. Tender never alters taxable gross or VAT.
